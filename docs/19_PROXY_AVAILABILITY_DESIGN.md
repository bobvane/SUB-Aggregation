## 一、当前检测链路的准确能力边界

### 1.1 现有能力（代码检查确认）

| 能力 | 来源 | 边界 |
|------|------|------|
| TCP 连通性 | `node:net` 三次连接（`probeNode` :186） | 仅证明"NAS → 服务器:端口"路径通，**不能**证明代理协议层可用 |
| TLS 握手 | `node:tls` 三次握手（同文件） | 仅证明 SNI/certificate 协商成功，**不能**证明 VLESS/VMess/Trojan/SS/SSR 等协议认证通过 |
| 协议层认证 | — | **无法检测**。端口开着但 token/ID 失效的节点会被判 `alive` |
| UDP 协议（hysteria2/tuic/wireguard） | `isProbeApplicable` 早退返回 `unknown` | 基础探测不适用，不写健康数据，不进自动配置（P0 闭环） |
| 吞吐量/带宽 | — | 未测 |
| 地理位置偏差 | ip-geo 数据（非探测结果） | 非探测结果 |

### 1.2 "部分节点被标记 alive 但实际经 Mihomo 代理失败"的根因

```
NAS TCP 探测路径：
  NAS ──TCP──> proxy_server:443  (握手成功 → alive)

Mihomo 实际代理路径：
  client ──VLESS/Trojan/SS──> proxy_server:443 ──隧道──> target

两者测试的是完全不同的网络段。TCP 可达 ≠ 代理可用。
```

### 1.3 状态语义定义（P1 复审新增）

明确区分以下四种状态，不得互相混淆，不得把未知转换为成功或失败：

| 状态 | 定义 | 当前来源 | 处理 |
|------|------|---------|------|
| **基础连通性成功** | TCP 连接或 TLS 握手成功（`alive`） | `probeNode` | 不等同于代理可用 |
| **基础连通性失败** | TCP/TLS 探测未达成功条件（`dead`/`timeout`/`error`） | `probeNode` | 状态机累计，3 轮确认 disabled |
| **不适用/未知** | 当前基础探测不适用的协议（UDP 类：hysteria2/tuic/wireguard） | `isProbeApplicable` 早退 | 标记 `unknown`，不累计失败，不进配置（未锁定时） |
| **真实代理可用性** | 必须由真实代理请求结果支持 | 当前**项目未实施**此验证 | 未实施时明确标示"项目未验证"，不得填成功或失败 |

**禁止行为**：
- 不得把 TCP/TLS 成功表述为 VLESS、VMess、Trojan、SS、SSR、AnyTLS、Hysteria2、TUIC 或 WireGuard 的代理协议验证成功。
- 不得把 `unknown`（不适用）计入失败比例，不得把 `unknown` 转换为"失败"。
- 不得假设客户端 `url-test` 的检测结果会自动回传至 SUB-Aggregation。

## 二、Mihomo 真实代理健康检查能力调研

### 2.1 官方功能（文档资料确认，NAS 实机待验证）

Mihomo 支持两种真实代理健康检查方式：

1. **配置层 url-test**：`proxy-groups[].type: url-test` 中的 url-test 组，Mihomo 定期向每个成员节点发起真实 HTTP 请求（指定 url），检测状态码并切换最优选。
   - 参数：`url` / `interval` / `timeout` / `tolerance` / `expected-status` / `max-failed-times`
   - 这是**客户端侧**功能，不暴露给订阅服务
   - 目标版本（≥v1.19.x）对 https url 支持：**待实机验证**（wiki 无法在线核实）

2. **external-controller API**：`GET /api/proxies/{name}/delay?timeout=5000`
   - 对指定代理组/节点执行一次真实代理延迟测试（通过该代理请求 url，计时）
   - 需要启动 Mihomo 并开启 external-controller
   - 响应 JSON：`{"delay": <ms>, ...}` 或 error
   - **这是方案 B 的技术基础**；external-controller 支持性：**待实机验证**

> ⚠️ 注意：以上两项均基于 Mihomo 官方文档（无法在本环境访问），实际行为须在目标 Mihomo 版本实机验证后方可确认。

### 2.2 协议覆盖能力（Mihomo 作为代理内核，文档资料确认）

Mihomo 完整支持的协议：

| 协议 | Mihomo 支持（文档） | 本项目生成器 | 当前 TCP/TLS 探测覆盖 |
|------|:-----------:|:------------:|:---------------------:|
| VMess | ✅ | ✅ | 部分（TCP 通 ≠ 协议通） |
| VLESS | ✅ | ✅ | 部分 |
| Trojan | ✅ | ✅ | 部分 |
| Shadowsocks | ✅ | ✅ | 部分 |
| SSR | ✅ | ✅ | 部分 |
| AnyTLS | ✅ | ✅ | 部分 |
| Hysteria2 | ✅ | ✅ | ❌（UDP，unknown） |
| TUIC | ✅ | ✅ | ❌（UDP，unknown） |
| WireGuard | ✅ | ✅ | ❌（UDP，unknown） |

**关键结论：Mihomo 对 9 种协议都有真实代理请求支持（文档确认），TCP/TLS 探测对 UDP 协议 3 种完全无效（代码确认）。协议覆盖的实际验证需 NAS 实机测试。**

## 三、三方案比较

### 方案 A：语义明确化 + `proxyUsable` 字段（**暂缓，无数据来源**）

**核心思路**：
- 当前 TCP/TLS 探测保留为「基础连通性」检测，语义明确为 `reachable`
- 新增字段 `proxy_usable`（默认 unknown/null），**仅**在通过真实代理验证后写入
- `getDroppedNodes` 双规则不变，基于 reachable 数据

**现状（P1 复审）**：
- 项目当前没有真实代理验证器（方案 B 未实施）
- 客户端 url-test 结果不回传项目（无回传机制）
- **没有数据来源** → `proxyUsable` 字段无法被可靠填充
- 本轮**不实施**：不新增 `proxyUsable` 数据模型字段、不写 `health:proxy:{fingerprint}`、不加评分维度、不加自动剔除规则、不依赖这些字段的前端列

**未来实施前提条件**（全部满足后重新评估）：
1. 明确的检测结果来源（方案 B 实施后才有数据来源）
2. 检测时间戳与有效期机制（过期结果不作为过滤依据）
3. 失败复核机制（避免单次失败即剔除）
4. 恢复机制（节点恢复可用后重新进配置）
5. 不与 `locked` 节点语义冲突（锁定节点优先级不变）

**协议覆盖**：
- 字段本身对协议无影响；数据来源取决于验证方案（A 无验证器，B 有验证器但需批准）

---

### 方案 B：隔离 Mihomo 实例对候选节点做真实代理健康检查（**需单独批准**）

**核心思路**：
- 在隔离容器/目录运行一个 Mihomo 实例（不接生产订阅），只包含「待验证节点池」
- 通过 external-controller API 对每个节点发起 `GET /api/proxies/{name}/delay`
- 验证结果写回 KV `health:proxy:{fingerprint}` 作为 `proxyUsable` 字段
- `getDroppedNodes` 扩展：`proxyUsable === 'no'` 的节点也剔除
- 生产配置生成时排除 `proxyUsable === 'no'` 节点

**优点**：
- 真正解决「端口通但协议异常」的误判
- 对 9 种协议都有覆盖（Mihomo 原生支持，文档确认）
- 可配置验证频率

**缺点与约束冲突**：
- 需要运行**第二套 Mihomo 进程**（与用户约束「不引入新常驻容器或第二套代理内核」直接冲突）
- 隔离实例需要单独的配置文件（与生产配置不同——生产配置无 external-controller，见 `src/generator/mihomo.ts:603` 注释）
- NAS 资源代价：每个 Mihomo 实例 ~30-50MB 内存（估算），验证时间取决于节点数
- 隔离实例的网络路径与生产客户端不同（NAS 出网 vs 用户设备出网），验证结果有限参考价值
- external-controller 裸开有安全风险（项目已有注释指出）

**最小可行实现代价（估算，实机待验证）**：
- Docker：临时容器，验证完成后销毁（不常驻）
- 容器镜像 ~80MB（估算），首次拉取耗时需实机确认
- 每次全量验证约 2-5 分钟（节点数 × timeout，估算）

**涉及文件（实施时）**：
- 新增 `src/services/mihomo-verify.service.ts`：生成隔离配置、启动容器、查询 delay API
- 修改 `src/services/config.service.ts`：`getDroppedNodes` 加 `proxyUsable==='no'` 规则
- 新增 `scripts/mihomo-verify-config.ts`：生成验证用独立 Mihomo 配置
- Docker 编排（临时容器，不常驻）

**注意**：本方案实施须用户单独批准，不得默认引入。

---

### 方案 C：由客户端 Mihomo 的 url-test 负责实际选优，项目只负责订阅整理和基础过滤（**推荐主方案**）

**核心思路**：
- 项目侧维持现状：TCP/TLS 基础探测 + 配置生成（url-test 组参数 P0 已优化）
- 客户端 Mihomo url-test 组（自动选择、地区组）负责实际选路和延迟比较
- 项目只确保「被剔除节点不进配置」，不判断「协议层是否可用」
- 文档及界面明确：基础连通性成功 ≠ 代理可用；客户端 url-test 是客户端侧检测，不是项目自身的协议层验证

**明确不宣称**：
- 客户端不会自动把 url-test 检测结果同步回项目
- 项目无法从客户端获取真实代理可用性数据

**优点**：
- 零新增部署复杂度，完全在现有架构内（代码检查确认）
- 客户端 Mihomo 的 url-test 天然测试真实代理路径（客户端到目标）
- 用户设备直连目标，结果更贴近实际使用体验
- 维护成本最低（只需验证 P0 已生成的 url-test 参数正确性）

**缺点**：
- 项目无法提前识别协议层异常节点（这类节点会在配置中，客户端 url-test 才排除）
- 如果所有节点协议层都异常，url-test 无有效节点可选

**协议覆盖**：
- 全部 9 种协议由 Mihomo url-test 覆盖（Mihomo 文档确认）
- 客户端侧覆盖完整

**涉及文件（实施时）**：
- 无新增代码，只需确认 `src/generator/mihomo.ts` 生成的 url-test 参数正确
- 文档更新：「节点实际可用性以客户端 Mihomo url-test 为准，项目不验证协议层」

**资源消耗说明**：
- 项目服务端：不新增任何常驻进程，因此不新增服务端常驻 CPU/内存开销（代码检查确认）
- 客户端：url-test 有客户端请求与资源开销（非项目服务端开销，由用户设备承担）
- 不得把"零新增"表述为"整体零开销"

## 四、推荐方案

### 推荐：方案 C 为主方案，方案 A 暂缓，方案 B 需单独批准

**理由**：

1. **方案 C 是架构上最合理的选择**：真实代理路径的延迟和可用性应由使用路径决定。客户端 Mihomo url-test 直接从客户端设备向目标测速，比 NAS 侧（可能出网路径不同）更准确。项目职责边界清晰：订阅整理 + 基础过滤 + 配置生成。

2. **方案 A 暂缓，因为无数据来源**：没有验证器（B 未实施）、没有客户端回传机制，`proxyUsable` 字段无法被可靠填充。强加字段只会制造一个永远为 `null` 的摆设字段，不增加实际价值。待 B 实施后，A 的字段设计可作为配套实现。

3. **方案 B 仅在用户明确需要「项目侧协议层验证」时启用**，违反「不引入第二套内核」约束，需用户单独批准。且隔离实例的网络路径与客户端不一致，验证结果参考价值有限。

### P1 实施范围（主方案 C）

1. 验证 P0 已生成的 url-test 参数（https URL、interval、tolerance、max-failed-types）在目标 Mihomo 版本中的正确性（**NAS 实机验证**，本阶段不执行）
2. 文档更新：「节点实际可用性由客户端 Mihomo url-test 负责，项目不验证协议层；基础连通性成功不代表代理可用」
3. 前端文案确认：P0 已完成的文案（「连通性 RTT / 非真实代理延迟 / 客户端 Mihomo 负责」）正确无误，无残留把基础连通误表达为代理可用的内容
4. 不做任何代码变更（方案 C 本身不需要新代码）

### 暂不实施（待用户批准）

- `proxyUsable` 字段（无数据来源，随方案 B 一起实施）
- 隔离 Mihomo 验证服务（方案 B，需用户单独批准）
- 自动剔除 `proxyUsable === 'no'` 规则（依赖 B）

### 5.1 验证项（每项含前置/步骤/观察点/预期/失败判定/是否需用户手动）

> 通用前置：测试客户端已导入 P0 生成的 mihomo 配置（独立副本），TUN 或系统代理模式，
> 可访问 Mihomo 日志与「测速」API（客户端内建面板）。

**V1 HTTPS `generate_204` 测速地址是否可用**
- 前置：确认客户端导入的是 P0 生成的 mihomo 配置副本（url-test 的 url 应为 `https://www.gstatic.com/generate_204`）；目标 mihomo 版本待用户提供
- 步骤：导入测试配置 → 等待一个 interval（300s）或手动触发一次测速 → 查看日志中 url-test 条目
- 观察位置：Mihomo 日志（含各 proxy 的 delay 数值或 error 文本）
- 预期现象（文档推断，待实机）：各节点记录到 ms 数值
- 失败判定：日志出现测速 error（如「unsupported scheme」/TLS 错误）→ 记录具体报错，https 不成立则需评估回退 http（另行决策，不在本轮）
- 是否需用户手动：是（导入配置、读日志）

**V2 顶层「自动选择」组 url-test 是否正常执行**
- 前置：V1 通过；测试配置顶层「自动选择」proxies = 扁平节点列表（P0 生成层已保证）
- 步骤：手动切换当前出口为「自动选择」→ 连续观察 2–3 个 interval → 看组内选中节点是否变化、面板是否显示延迟
- 观察位置：面板 proxy-groups「自动选择」当前选中项 + 各节点 delay 列
- 预期现象（待实机）：选中节点为 delay 最小者；切换不报错
- 失败判定：组无任何延迟数值（全 error）→ 记录哪些节点失败及原因
- 是否需用户手动：是

**V3 地区组测速与切换**
- 前置：某地区组（如「🇭🇰 香港」）有 ≥2 节点
- 步骤：对地区组执行一次手动测速（面板按钮）→ 观察选中节点是否为最快者
- 观察位置：地区组 delay 列与当前选中项
- 预期现象（待实机）：最快节点被选中
- 失败判定：延迟列全空/全 error → 记录
- 是否需用户手动：是

**V4 GLOBAL 与默认选择在有/无节点两种情况的行为**
- 前置：正常测试配置（各地区有节点）+ 一份删除某地区全部节点后的测试配置副本
- 步骤 a：正常配置下手动切到 GLOBAL → 看 GLOBAL 候选是否含各地区组名 + DIRECT
- 步骤 b：删地区副本下，访问需走代理的站点 → 观察是否回落、日志报错情况
- 观察位置：面板 GLOBAL 候选列表；浏览器/测速结果；Mihomo 日志
- 预期现象（待实机）：a) GLOBAL 正常列出组名；b) 空地区组不导致整个配置崩溃（具体回落行为记录实测）
- 失败判定：配置加载报错或客户端崩溃 → 停止该步，记录报错原文
- 是否需用户手动：是
